Where Presence stands, and what comes next

A job-search companion people run themselves — status of the build as of 12 September 2026, with the work still ahead.

Prepared for Denis Baldakov (product owner) · internal, shareable with collaborators · companion documents: Values (2), Student track (3)

1. In one paragraph

Presence is the productisation of a personal job-hunt automation that has run in production since 13 August 2026 (six scheduled agents, seven job-source connector types, a 612-row application tracker, a Telegram delivery loop, and — since 12 September — automatic reading of application-status emails). The product keeps what made that system work and strips the rest: one source, two agents, one messenger, a small tracker core, everything essential free forever, and a charter enforced in code. Four of eight workstreams are complete; the runtime has been proven live against a frontier API and a free local model; the connector-to-tracker path is proven end to end. The next work is delivery (Telegram), then the agent packs that turn plumbing into judgment.

2. What has been decided

DecisionOutcome
What it isAn open, local-first operating system for the job hunt (and the study years before it): AI agents + a tracker with conventions + training tools + messenger delivery, run on the user's own machine and keys. The "Home Assistant model", aimed at careers.
v1 shape (canonical spec: Presence_Architecture.pdf)Exactly one source (LinkedIn, library-based search), two agents (Scout, Brief), SQLite tracker, Telegram, BYO model key (Anthropic / OpenAI / Ollama — the zero-cost path), Docker, onboarding as a conversation (CV upload → parsed draft → five questions → confirm).
Business modelEverything essential is free, forever — no tiers, no subscriptions. Funding by voluntary support (Patreon / GitHub Sponsors / Open Collective). Paid may only ever be "extra, not essential". Training sims and drills are editable packs in the free core.
Charter (enforced by tests)A human clicks every Submit · no invented facts · data stays on the user's machine · spending is capped daily.
LicensingAGPL-3.0 core; MIT for pack and SDK formats so community content stays frictionless.
Repositorygithub.com/Sofa3xpert/presence, private for now, single contributor, CI (lint · tests · Docker build) green on every push. Commit history is minimal and product-focused.
Tracker schemaSmall fixed engine core plus an uninterpreted extra field per job; new features become new interpreters, not migrations.

Precision-first dedupe: same link key merges; identical title merges only when one side has no link; two different links are two postings. Validated read-only against the real 612-row sheet.
W3ConnectorsOne connector interface with a registry; LinkedIn connector on python-jobspy with per-query error isolation; queries built from search.yaml (freshness window, blocklist, results cap); seen-postings store so a judged posting never resurfaces; live check ran a real search of 10 postings straight into a tracker.
Test suite: 43 tests, none touching the network. Tooling lesson recorded: an environment "doctor" script and test-path independence were added after a macOS venv quirk cost debugging time.

5. Backlog beyond v1 (recorded, not scheduled)

  • Email-alerts connector — the customer's saved-search alert emails as a second source; the registry already has the slot.
  • Status-mail loop — reading application outcomes from the mailbox (read-only scan → agent judgment → one guarded writer). Built and running in the personal pipeline since 12 September; ports almost as-is.
  • Training studio — assessment drills, interview sims with an AI facilitator, daily problem sets; v1 ships only the pack format. Also the natural meeting point with the student track (Document 3).
  • More sources (ATS public APIs, region watchlists), Sheets/Notion tracker backends, WhatsApp/Discord adapters, desktop app packaging, an optional hosted runner — all explicitly later.

6. Open questions and risks

  • Judgment on cheap models — how much of Scout's keep/drop/tier quality survives on a local 9B model is unknown until the eval harness exists (W5). Decide by measurement, not opinion.
  • Board scraping is terms-of-service grey. v1 accepts it as the pragmatic start (each user runs as themselves); the clean channels (email alerts, public ATS APIs) are the strategic direction.
  • Brief timing and volume — one digest versus instant pings for top-tier finds; decide during W4/W6 with real use.
  • "Anywhere" versus "no service" — a phone-only user cannot self-host; the hosted runner stays an optional convenience decided later.
  • Time — the job hunt outranks product weeks; milestones are self-contained so pauses cost nothing but calendar.
